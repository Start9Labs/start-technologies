# AGENTS.md — start-core

The shared Rust backend lib (`start-core`, lib name `start_core`) at `shared-libs/crates/start-core`.
All six product bins (`startbox`/`startd`, `start-container`, `start-cli`, `registrybox`,
`tunnelbox`, `startwrt`) link against it; all but `startwrt` are thin wrappers in the product
crates (`startwrt` is a full backend of its own that imports this crate aliased as `startos`).

`CLAUDE.md` is a one-line `@AGENTS.md` import. See [ARCHITECTURE.md](ARCHITECTURE.md).

## Layout

- This is a library; entrypoints live in `src/bins/` and are selected by each product wrapper's
  `MultiExecutable`. Don't add a new top-level binary here — add an entrypoint and enable it from
  the product crate.
- Generated TS lands in `bindings/` (gitignored, regenerated by `make start-core-ts-bindings`); never hand-edit it.
- The whole backend is one crate `src/` tree.

## Build & test (run from the repo root)

Install stable Rust and Docker. `rust-analyzer` is recommended.

- `cargo check -p start-core` — type-check the library.
- `make start-core-test` — run the test suite (wraps `run-tests.sh`, which uses the `rust-zig-builder`
  container and the `test` feature; skips `export_` tests). Or run a single test directly:
  `cargo test -p start-core <name> --features=test`.
- `make start-core-format` — format the shared Rust crates with the pinned nightly container (`make start-core-format-check` checks formatting). Set `FMT_NATIVE=1` only when that nightly is installed locally.
- `cargo build -p start-os --bin startbox` (or the other product crate/bin) to build a binary.

Keep `README.md`, `ARCHITECTURE.md`, this file, and the topical references current when changing
project structure, conventions, build process, or product context.

## Adding an RPC endpoint

1. Define serializable request and response types.
2. Choose a handler type (`from_fn_async` for most cases).
3. Write the async handler.
4. Register it in the appropriate `ParentHandler` tree.
5. Derive `visit_rs::TS` for reachable params/results. Use `#[ts(export)]` for standalone shared DTOs.

See [rpc-toolkit.md](rpc-toolkit.md) for handler patterns.

## Gotchas

- **Process invocation: use `.invoke(ErrorKind::...)`, not `.status()`.** When running CLI commands via `tokio::process::Command`, the `Invoke` trait (from `crate::util::Invoke`) captures stdout/stderr and checks exit codes. `.status()` leaks stderr directly to system logs and creates noise in production. For check-then-act patterns (e.g. `iptables -C`), use `.invoke(...).await.is_ok()` / `.is_err()` instead of `.status().await.map_or(false, |s| s.success())`.
- **File I/O: prefer `crate::util::io` over `tokio::fs`** when an equivalent helper exists. These helpers add error context and mount-aware behavior that `tokio::fs` doesn't.
- **i18n is mandatory for any user-facing string** — including CLI subcommand descriptions (`about.<name>`), CLI arg help (`help.arg.<name>`), error messages, notifications, and setup messages. All 5 locales (`en_US`, `de_DE`, `es_ES`, `fr_FR`, `pl_PL`) must be filled in `locales/i18n.yaml` (i.e. `shared-libs/crates/start-core/locales/i18n.yaml`), alphabetically ordered within their section. Use `t!()`, match the key namespace to the module path, and use kebab-case for multi-word segments. See `i18n-patterns.md`. Compile-time validation catches missing keys.
- **Wire-schema changes need a multi-step rebuild.** `visit_rs::TS` follows directional serde shapes; inputs normally use `FooInput`, outputs `Foo`. Use `#[serde(rename_all = "camelCase")]` for wire field names. Reference the actual custom decoder or serializer through `#[visit(input_wire = "RustType")]` / `output_wire`; a common `#[ts(wire = "RustType")]` serves both directions. Literal `ts(type)` is for deliberate projections. Owning crates supply scalar representations; JSON integers render as numbers. Run `make start-core-ts-bindings` (the generator example emits all actual server trees and inventory-owned standalone namespaces, then rsyncs into `shared-libs/ts-modules/start-core/lib/osBindings/`), followed by `cd shared-libs/ts-modules/start-core && make dist` and `cd projects/start-sdk && make bundle` before web/runtime checks. See [ARCHITECTURE.md](ARCHITECTURE.md#cross-layer-verification).
- **A change to the CLI surface needs `make manpages`.** Adding or renaming a subcommand, or editing the `about.*`/`help.arg.*` key behind one, changes the committed man pages under `projects/*/man/` — a new subcommand adds a page _and_ a line to its parent's. The `Generated Artifacts` CI job regenerates them and fails on any drift, in the same job as the TS bindings, so a CLI change and a `#[ts(export)]` change each need their own regeneration step. Note the gate reads `git status`, so staging the result is not enough — commit it.
- **Bindings come from compiled production handlers.** `examples/generate_bindings.rs` generates StartOS/setup/init/diagnostic/registry/tunnel/effects trees and both standalone namespaces. `#[ts(export, namespace = "tunnel")]` owns a tunnel root; no parallel export list exists. Core enables `rpc-toolkit/ts`; inspected CLI/container-only handlers use `no_ts()`. The `Generated Artifacts` CI job regenerates bindings and man pages, uploads stale artifacts, and fails on drift. Pass `CARGO_BUILD_JOBS` to cap compiler concurrency without changing fingerprints.
- **Read [policy-routing.md](policy-routing.md) before touching an `ip rule`, a gateway routing table, a packet or connection mark, or `rp_filter`/`src_valid_mark`** (`src/net/gateway.rs`, `net_controller.rs`, `transparent.rs`, `wifi.rs`). It holds the invariants the rule order is derived from and the procedure for changing it.
- **Version bumps** follow [VERSION_BUMP.md](VERSION_BUMP.md); the crate version in `Cargo.toml` is tagged `# VERSION_BUMP`.
- **`--version` reports the product, not the platform.** The shared bins set clap's `--version` to `bins::product_version()`, seeded from each product wrapper's own crate `CARGO_PKG_VERSION` via `PRODUCT_VERSION.set(...)` in its `main()`. Don't wire `--version` back to `Current::semver()` (the StartOS platform/migration version) — that's wrong for `start-cli`/`start-registry`/`start-tunnel`, which version independently. The `start-cli` applet is special: it reports `bins::cli_version()` — the `start-cli` crate version baked in by `build.rs` from `projects/start-cli/Cargo.toml`, not `PRODUCT_VERSION` — because `startbox` bundles it alongside the OS daemon under the OS's `PRODUCT_VERSION`, so the OS's `start-cli` (a symlink to `startbox`) would otherwise report the OS version. Baking it in start-core (which hosts the applet) also fixes the generated man page, which is rendered by an `export_manpage_*` test in this crate where no wrapper `main()` runs. `start-container` works the same way for the same reason — it ships only in start-os, so it reports `bins::startos_version()` (the OS version, baked by `build.rs` from root `package.json`, which is its source of truth — no `Cargo.toml` can hold a four-segment version like `0.4.0.1`).
- **Do not edit `CLAUDE.md`** — it is a one-line `@AGENTS.md` import. Edit this file instead.
